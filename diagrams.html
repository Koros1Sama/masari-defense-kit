هذه الرسمة ليست من مخططات UML القياسية، بل هي مخطط عملية (Process Diagram) يشرح كيف نظّمنا عملنا في تطوير المشروع. المنهجية الرشيقة (Agile) تقسّم المشروع إلى تكرارات قصيرة (Sprint / Iteration)، كل تكرار يمرّ بنفس المراحل: تحليل ← تصميم ← تنفيذ ← اختبار ← مراجعة ← تغذية راجعة. نستخدمها بدل نموذج الشلال (Waterfall) لأن المتطلبات كانت ستتغيّر بعد رؤية النموذج الأولي (Prototype). الرموز بسيطة: مستطيل = مرحلة، سهم = انتقال، سهم يرجع للخلف = إعادة الدورة (تكرار جديد).

🔍 كيف تقرأ هذه الرسمة؟

ابدأ من المستطيل رقم ① واتبع الأسهم بالترتيب ② ③ ④ ⑤ ⑥. في النهاية لا تتوقف عند ⑥: اتبع السهم الراجع المكتوب عليه «تكرار Sprint جديد» الذي يعود بك إلى ① — هذه هي فكرة الرشاقة: الدورة تتكرر. ثم اقرأ السطر التحت للرسمة: هو يخبرك كيف طُبّقت الدورة فعليًا في مساري عبر 4 تكرارات حقيقية.

🎯 أسئلة متوقعة عنها

لماذا اخترتم الرشيق (Agile) ولم تختاروا الشلال (Waterfall)؟
الإجابة:

لأن المشروع تفاعلي ولم يكتمل تصوّر واجهته وآلية الاستثناءات إلا بعد رؤية نموذج أولي، والرشيق يتحمّل تغيّر المتطلبات عبر التكرارات، بينما الشلال لا يرجع للخلف. كما أتاح الرشيق عرض نسخة تعمل مبكرًا وتطوير المكوّنات الأربعة بالتوازي ثم الدمج في نهاية كل تكرار.

كم تكرارًا نفّذتم وماذا أنجز كل واحد؟
الإجابة:

أربعة: (1) بيانات الخريطة وخوارزميات البحث، (2) الخادم الخلفي وواجهات REST، (3) العميل الأمامي التفاعلي، (4) دمج المساعد اللغوي وتحسينات الأمان وتجربة المستخدم.

ما فائدة مرحلة التغذية الراجعة ⑥؟
الإجابة:

هي التي تغلق الحلقة: نستلم ملاحظات على النسخة المدمجة ونحوّلها إلى متطلبات معدّلة في تخطيط التكرار التالي، فالمنتج يتحسّن تدريجيًا بدل أن نكتشف المشاكل في النهاية.

كيف وزّعتم العمل وأنت أربعة؟
الإجابة:

كل عضو تقدّم في مكوّنه باستقلال (خوارزميات / خادم / واجهة / مساعد لغوي) بالتوازي، والدمج يجري في مرحلة ⑤ المراجعة والدمج في نهاية كل تكرار.

رسمة 02مخطط حالات الاستخدام (Use Case Diagram)Use Case Diagram

تكبير↗
🎓 النظرية من المنهج

رسمة UML سلوكية تُظهر الفاعلين (Actors) وحالات الاستخدام (Use Cases) اللي يقدمها النظام، وهي تصوّر المتطلبات الوظيفية (Functional Requirements) بشكل بصري. الفاعل = إنسان أو نظام يتعامل مع نظامنا (خارجه). حالة الاستخدام = وظيفة كاملة يحققها الفاعل مع النظام. العلاقات: Association (خط يربط فاعلًا بوظيفة)، «include» (الوظيفة الأساسية تحتوي دائمًا وظيفة فرعية — السهم من الأساسية إلى الفرعية)، «extend» (وظيفة اختيارية تضيف سلوكًا لأساسية — السهم من الاختيارية إلى الأساسية). الإطار الخارجي = حدود النظام (System Boundary).

🔍 كيف تقرأ هذه الرسمة؟

أول شي حدّد الفاعلين: العصويون (stick figures) برا الإطار — عندنا «مستخدم عادي» يمين و«مشرف Admin» يسار. ثاني شي كل خط (Association) من فاعل إلى بيضة (Oval) معناه هذا الفاعل يستخدم هذه الوظيفة. ثالث شي الأسهم المتقطعة المكتوب عليها «include» تعني: الوظيفة اللي يخرج منها السهم تشتغل دائمًا معها الوظيفة اللي يدخل إليها. والسهم المكتوب عليه «extend» (من استثناء شارع/مكان إلى تخطيط المسار) معناه ميزة اختيارية تُضاف أحيانًا. الإطار المتقطع الكبير = حدود نظام مساري، والملاحظة تحت تقول الضيف هو نفسه المستخدم قبل الدخول.

🎯 أسئلة متوقعة عنها

ما الفرق بين include و extend في رسمتك؟
الإجابة:

include إجبارية: تسجيل الدخول يشمل دائمًا إصدار توكن، وتخطيط المسار يشمل دائمًا تنفيذ الخوارزمية والحفظ في السجلّ. extend اختيارية: استثناء شارع/مكان يمدّ تخطيط المسار فقط عندما يطلب المستخدم التجنّب — يمكن تخطيط مسار بدون أي استثناء.

لماذا «حفظ في سجلّ الرحلات» يستقبل سهمي include من وظيفتين؟
الإجابة:

لأنه يُستدعى من مسارين: من تخطيط المسار (يُكتب السجلّ بعد كل بحث ناجح) ومن عرض سجلّ الرحلات (قراءة السجلّات المحفوظة سابقًا) — وظيفة فرعية مشتركة وهذا هو الغرض من include إعادة الاستخدام.

لماذا لم تجعلوا الضيف فاعلًا منفصلًا؟
الإجابة:

لأن الضيف يقوم بنفس وظائف المستخدم العادي (خريطة، مسار، أمر لغوي) مع تقييد المزايا التي تحتاج مصادقة كالسجلّ، فأبقيناه مستخدمًا واحدًا قبل الدخول ووضّحنا ذلك بملاحظة على الرسمة، وهذا أبسط وأصح نمذجة.

لماذا المشرف متصل بوظيفة واحدة فقط؟
الإجابة:

لأن دوره الوحيد إدارة الخريطة CRUD — إضافة وتعديل وحذف العقد والوصلات؛ لا يخطّط مسارات ولا يستخدم NLU، وهذا تطبيق لمبدأ فصل الصلاحيات (Authorization) المذكور في تصميم الأمان.

وين تظهر المتطلبات غير الوظيفية هنا؟
الإجابة:

لا تظهر — مخطط الاستخدام يغطي الوظيفي فقط (FR-1 حتى FR-11 تقريبًا). غير الوظيفية كالأداء والأمان موجودة في جداول المتطلبات، أما التوكن الموقّع والأمان فيظهر أثره كوظيفة مُضمّنة (إصدار توكن موقّع).

رسمة 03مخطط الكيانات والعلاقات (ERD)Entity-Relationship Diagram (ERD)

تكبير↗
🎓 النظرية من المنهج

رسمة تُمثّل بنية قاعدة البيانات العلائقية (Relational Database) قبل إنشائها: كل مستطيل = كيان/جدول (Entity/Table)، وداخله الحقول (Attributes) مع نوع بيانات كل حقل، والمفتاح الأساسي (PK — Primary Key) يميّز الصف، والمفتاح الأجنبي (FK — Foreign Key) يربط الجدول بجدول آخر. الخطوط بين الجداول = علاقات مع عدد الكاردينالية (Cardinality) مثل 1—N (واحد إلى متعدد). يُستخدم في مرحلة التصميم لبناء مخطط SQLite/SQL.

🔍 كيف تقرأ هذه الرسمة؟

عدّ الجداول أولًا: أربعة. لكل جدول اقرأ من فوق لتحت: أول حقل غالبًا هو PK (المعرّف الفريد)، والحقول المكتوب أمامها FK هي روابط لجداول أخرى — السهم في FK يوضح يشير إلى أي جدول وأي حقل بالضبط. ثم انظر للخطوط بين الجداول واقرأ الكاردينالية المكتوبة عليها: (1 — N) تعني صف واحد يرتبط بعدة صفوف، و(N — N) بين map_nodes و map_edges تعني الوصلة تربط عقدتين. السطر العلوي يلخّص لك معنى العلاقتين بكلام عادي.

جدول users (المستخدمون)PK id : INTEGER — UQ username : TEXT (فريد) — password_hash : TEXT (كلمة مرور مشفّرة) — created_at : TEXT. يحفظ الحسابات.

علاقة 1 — N بين users و search_historyمستخدم واحد له عدة عمليات بحث، وكل سجلّ بحث يعود لمستخدم واحد — عن طريق user_id.
علاقة N — N بين map_nodes و map_edgesالوصلة تربط عقدتين (u و v)، والعقدة الواحدة تشارك في عدة وصلات — map_edges هو جدول الربط.

«هذا مخطط الكيانات والعلاقات لقاعدة بيانات SQLite — أربعة جداول. أبدأ بـ users: معرّف id أساسي، واسم مستخدم username فريد، وكلمة المرور محفوظة hash فقط مش نص صريح، وتاريخ إنشاء. منه علاقة واحد إلى متعدد 1—N مع search_history: كل بحث يحفظ user_id كمفتاح أجنبي يشير إلى users.id، فمستخدم واحد له عدة عمليات بحث. وفي search_history نخزّن النص الأصلي command، والوجهة destination، والخوارزمية algorithm، والمسار path بصيغة JSON، والتكلفة cost، والوقت. ثم جدولا الخريطة: map_nodes وفيه id نصي مثل Sanaa_Uni والاسم العربي name وإحداثيا x و y — والإحداثيات ضرورية لأن منها نشتق وزن الوصلة وحساب الكاشف heuristique. و map_edges فيه مفتاحان أجنبيان u و v كلاهما يشير إلى map_nodes.id مع اسم الشارع street — فالعلاقة بين العقد والوصلات N—N: الوصلة تربط عقدتين، والعقدة تدخل في عدة وصلات. ملاحظة مهمة: الوزن غير مخزّن في الجدول — يُحسب من المسافة الإقليدية بين إحداثيّي العقدتين مقسومة على 10، وهذا يضمن أن كاشف A* قابل للقبول.»

🎯 أسئلة متوقعة عنها

لماذا id في map_nodes نصي (TEXT) بينما في باقي الجداول رقمي؟
الإجابة:

لأن معرّف العقدة اسم دال مثل Sanaa_Uni أو Hadda يُقرأ مباشرة في الكود وفي نتائج المسار، فالنصي أوضح للتصحيح والربط، بينما users و search_history و map_edges صفوف تُنشأ تلقائيًا فالرقم التلقائي (AUTOINCREMENT) أنسب لها.

أين مخزّن وزن الوصلة (weight) ولماذا؟
الإجابة:

لماذا تظهر خطوة إعفاء البداية والوجهة قبل البحث؟
الإجابة:

لمنع التناقض: لو استثنى المستخدم شارع البداية نفسها لانقطع المسار قبل أن يبدأ. فالنظام يعفي نقطتَي الطرفين دائمًا من الاستثناء — ضمان وصول الطرفين مذكور في توصيف FR-3 و FR-4.

ما الفرق بين مسارَي الخطأ في الرسمة؟
الإجابة:

خطأ المدخلات: عقدة غير موجودة ← HTTP 400 (مشكلة طلب خاطئ). وفشل البحث: مسار مقطوع بالاستثناءات ← استجابة طبيعية found=false في PathResult (ليست خطأ برمجيًا بل نتيجة «لا يوجد مسار»).

لماذا فرعا A* و UCS متوازيان ثم يلتقيان في حلقة واحدة؟
الإجابة:

لأن الاختلاف بينهما في دالة الأولوية فقط (f = g + h مقابل g) — أي في طريقة الترتيب في الطابور، أما خطوات الحلقة الأربع فمشتركة. هذا حرفيًا ما يطبّقه نمط Strategy: نفس الهيكل، استراتيجية مختلفة.

أين يُطبَّق الاستثناء داخل الخوارزمية؟
الإجابة:

في الخطوة ② من حلقة البحث: عند توليد الجيران تُتجاهل أي وصلة شارعها في avoid أو جارها في avoid — فالبحث لا يمر فيها أصلًا بدل-filter النتيجة في النهاية.

لماذا الحفظ مشروط بـ«إن مسجّل»؟
الإجابة:

لأن جدول search_history مرتبط بـ user_id كمفتاح أجنبي إلى users — الضيف بلا حساب فلا سجلّ يُكتب له، وهذا متوافق مع ملاحظة مخطط التتابع.

الإجابة:

رسمة معمارية (ليست UML قياسية) تُظهر التقسيم الفيزيائي والمنطقي للنظام: منصّتان منفصلتان — عميل وخادم (Client–Server) — تتصلان عبر واجهات RESTful API بتنسيق JSON/XML. داخل الخادم طبقات متمايزة (Layers): الواجهة ثم المنطق ثم الوصول للبيانات ثم القاعدة — كل طبقة مسؤولة عن شيء واحد (مبدأ SRP). الرموز: الإطار المتقطع = منصّة/حدود نشر، المستطيل = مكوّن، الشريط الأصفر = قناة الاتصال، والأسهم = اتجاه الاعتماد والاستدعاء.

🔍 كيف تقرأ هذه الرسمة؟

اقسم الرسمة أفقيًا ثلاث مناطق: فوق إطار المنصّة 2 (العميل)، المنتصف شريط RESTful API الأصفر (قناة الاتصال الوحيدة)، وتحت إطار المنصّة 1 (الخادم). في العميل اقرأ المكوّنات الثلاثة يسارًا-يمينًا. في الخادم انزل طبقة طبقة من فوق لتحت — كل طبقة لا تتعامل إلا مع ما تحتها، والأسهم (يستخدم/يستدعي) تبيّن الاتصال، وسهم REST في الوسط يربط HTTP fetch فوق بـ API Layer تحت. Groq API خارج إطار الخادم لأنه خدمة اختيارية خارجية.

«هذه معمارية النظام: منصّتان منفصلتان تتحدثان عبر REST. أبدأ من فوق — المنصّة 2 العميل الأمامي في المتصفح: HTML و CSS و JavaScript بدون أي خطوة بناء. فيه ثلاثة مكوّنات: الشاشات الاثنتا عشرة مع Hash Router للتنقل، والخريطة التفاعلية بـ SVG التي ترسم 17 عقدة و 21 وصلة وتلوّن المسار فوقها، ثم HTTP fetch التي ترسل كل الطلبات ومعها التوكن وتستقبل JSON. بين المنصّتين الشريط الأصفر: RESTful API بتنسيق JSON و XML — قناة الاتصال الوحيدة، فلا يلمس العميل قاعدة البيانات أبدًا. وتحت — المنصّة 1 الخادم الخلفي: Python و FastAPI يعمل على uvicorn، بأربع طبقات أنزل فيها واحدة واحدة: طبقة الواجهة API Layer وفيها كل المسارات من /api/auth إلى /api/command؛ ثم طبقة المنطق وفيها nlu بمساريه Groq و rules و Router بخوارزميتي A* و UCS بنمط Strategy، وبجواره CityMap الرسم البياني للخريطة كنسخة Singleton؛ ثم طبقة الوصول للبيانات بنمط Repository: مستودعان يحيطان بالقاعدة؛ وأخيرًا SQLite في ملف masari.db بالجداول الأربعة. و Groq API مرسوم خارج إطار الخادم ومكتوب عليه اختياري — لأن النظام يعمل كاملًا بدونه بالقواعد. والفائدة الكبرى: الذكاء (الخوارزميات والخريطة) في وحدات مستقلة يعاد استخدامها حتى في مساق الذكاء الاصطناعي.»

🎯 أسئلة متوقعة عنها

لماذا فصلتم العميل عن الخادم في منصّتين؟
الإجابة:

ثلاث فوائد: تطوير كل منصّة باستقلال (فريق الويب لا ينتظر الخادم)، وعمل العميل على أي متصفح بلا قيود لغة لأن REST لغة-محايد، والأمان: لا قاعدة بيانات في المتصفح ولا كود خادم مكشوف للعميل.

لماذا طبقات داخل الخادم وما فائدتها؟
الإجابة:

أربع طبقات: API Layer للطلبات، المنطق للخوارزميات و NLU، Repository للبيانات، SQLite للتخزين — كل طبقة مسؤولية واحدة (SRP)، فتسهل الصيانة والاختبار: نختبر المنطق بمحاكاة المستودعات دون قاعدة حقيقية، ونستبدل أي طبقة دون كسر الباقي.

لماذا Groq API خارج إطار الخادم و«اختياري»؟
الإجابة:

لأنه خدمة سحابية خارجية لا نتحكم بها ولا ننشرها مع نظامنا، والنظام لا يعتمد عليها: عند غياب المفتاح أو الإنترنت يعمل المسار القاعدي rules تلقائيًا — لذلك رسمناه خارج الحدود ومكتوبًا عليه اختياري.

أين تعيش الخوارزميات ولماذا؟
الإجابة:

في طبقة المنطق داخل وحدات مستقلة (shared) يستوردها الخادم — منفصلة عن قواعد الويب و FastAPI، فلا تختلط بالتوجيه والاستجابات، وتُعاد استخدامها كما هي في مساقات أخرى كالذكاء الاصطناعي.

لماذا XML و JSON معًا؟
الإجابة:

متطلب FR-11 لتنوّع صيغ البيانات: الافتراضي JSON للواجهة الأمامية خفيف وجاهز في JavaScript، ونقطة /api/map.xml تخدم صيغة XML لمستهلكين آخرين أو أدوات تحليل — طبقة العرض نفسها بصيغتين.
